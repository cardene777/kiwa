回帰判定を 1 実行遅らせ、一度きりの跳ねと持続的なずれを分ける。

`regressed` / `improved` と判定した実行の比を、その場で履歴に積むか捨てるかを決めずに `pendingRatio` として預ける。
次の実行が同じ方向でなければ「一度きりの跳ね」として履歴に移し、同じ方向が続けば「持続的なずれ」として捨てる。

**なぜ必要か。**

従来は `stable` の実行だけを履歴に積んでいた。
この規則は 2 つの欠陥を同時に持つ。

1 つ目は、幅の推定が裾を失うこと。
上限を超えて動いた実行は定義上積まれないので、幅は「内側に収まった実行だけ」から作られる。
実測では幅 3.7% と記録された op が 20% 超動いていた。

2 つ目は、幅が一度も推定されない op が出ること。
自然な振れ幅が 20% を超える op は初回の比較で `regressed` になり、積むものがないまま永久に相対閾値だけで判定される。
6 パスの実測で 4 op がこの状態だった。

どちらも「一度きりの跳ねか、持続的なずれか」を判定の時点では区別できないことが根にある。
区別できるのは次の実行で、跳ねなら戻り、ずれなら続く。

**gate の条件が変わる。**

`regressionGate: true` で落ちるのは `regressed` が 2 回続いた時だけになった。
全 493 op を 6 パス測った実測で、gate が落とす件数は 18/19/21/6/27/21 から 0/3/2/4/4/2 に下がる。
判定そのものも 11/14/9/7/14/9 に下がる (幅に裾が入るため)。

report には `regressed — 1 回目 (次も続けば gate)` / `regressed — 2 回連続` と出るので、落ちなかった理由も読める。

**API の追加。**

- `OpOutcome.sustainedRegression` — 同じ方向の判定が 2 回続いたか
- `MeasureResult.pendingRatio` / `pendingVerdict` / `pendingSustained` — baseline に預けた比と方向、および既に持続と判定済みかの印
- `resolvePendingRatio()` — 預かりを今回の判定で解決する

**挙動の変更 (既存 API)。**

`runPerf3Layer` は op 名が重複した入力を例外にする。
baseline の記録は `${op.name}.serial` で引くため、重複すると記録と履歴が後の op で上書きされ、前の op の預かりを後の op が読む。
repo 内 251 個の perf 定義を走査して重複は 0 件だったので、実際に落ちる呼出は無い。

`regressionGate` の既定は false のまま。
残る 7 op のうち `vector` の `queryNearestTop5` は anchor から一方向に約 25% ずれ続けており、幅の推定では解けない (anchor の測り直しが要る)。

履歴が揃うまでの実行回数は増えない。
`stable` の実行は従来どおりその場で積むため、3 パスで 3 件に達する。
判定に幅が効き始めるのが 4 パス目なのは、判定がそのパスの書込み前の baseline を読むためで、本変更の前からそうだった。

`regressed` を挟む op ではむしろ速くなる。
従来は何も積まなかった実行が、次の実行で方向が変われば 1 件を積むようになる。
