# カバレッジと実行時間の契約

test を生成する skill が共通で従う契約。 各 SKILL.md は `## 完了条件` に本 file への
参照を 1 行書き、判定基準をここに一本化する。

## カバレッジは 100% を目指す

**閾値ではなく目標**。 `scripts/check-coverage-gates.mjs` の固定閾値
(lines / statements / functions 90%、branches 80%) は退行を止めるための下限で、
目指す先ではない。

`coverage-high-water.json` の ratchet は単調性を保証する = 一度上げた値は下がらない。
つまり **毎回 1 歩でも進めれば必ず 100% に着く**。

数える対象は 3 種すべて。

| 種別 | 数えるもの |
|---|---|
| statement | 未実行の文 |
| branch | 未通過の分岐 (**path 単位**、分岐単位で 1 に潰さない) |
| function | 未呼出の関数 |

**statement だけ数えると達成を偽る**。 実測で statement のみだと 12 package / 181 件、
3 種を足すと 22 package / 678 件になり、10 package が丸ごと隠れた。
`packages/perf-harness` は未実行 statement 0 件 / 未通過 branch 49 件で、
statement しか見ないと「もう埋まっている」 と表示される。

## 届かない時は理由を書く

**「届きませんでした」 で終わらせない**。 残ったものを 4 分類のどれかに割り当て、
report に理由を書く。

判定は上から順に試す。

| # | 分類 | 判定の仕方 | 対処 |
|---|---|---|---|
| 1 | 別の gate が覆っている | その行を変異させて `check-mutation-gates.mjs` が落ちるか確かめる | 変異試験が覆うことを code comment に残す |
| 2 | 実装が到達不能 | 入力は組めるのに、手前の条件でその分岐へ制御が渡らない | **実装を直す**。 到達しない分岐は実装の欠陥 |
| 3 | 入力を組めない | 防御的分岐で、型 / 引数の制約から到達する入力を作れない | 覆えないことを code に明記して残す |
| 4 | 単に書いていない | 上の 3 つに当たらない | 書く。 これが gap の本体 |

### 2 と 3 を混ぜない

どちらも「入力で通せない」 に見えるが、**2 は入力を組めるのに実装が到達しないので直せる**、
3 は入力そのものを組めないので直せない。

混ぜると対処が「明記して残す」 に倒れ、直すべき欠陥が受容される。
切り分けは「その分岐に届く入力を組めるか」 → 組めるなら「その入力で実際に制御が渡るか」 の順。

### 1 を「他が見てるから不要」 と読まない

分類 1 は「変異試験が同じ欠陥を捕まえる」 という事実の記録で、その行を覆う必要が無いという
判断ではない。 変異試験の threshold が下がれば覆いが外れる。

### 分類は提案、採否は user

分類 2 は実装の削除を伴い、分類 3 はその行を恒久的に対象外にする宣言になる。
どちらも後戻りしにくいので、AI が黙って決めない。

`/auto` 中は AskUserQuestion が抑止されるため、follow-up Issue を起票して番号を報告する。

## 手順

```
1. /kiwa-gap --metric coverage --package {pkg}     ← 残りを安い順に並べる
2. gap があれば /kiwa-loop --metric coverage       ← 先頭 1 件を埋めて再測
3. 残ったものを /kiwa-verdict で分類し report に書く
```

`/kiwa-loop` は「未達 0 件」「改善 0 が 2 round 連続」「上限 5 round」 のいずれかで必ず止まる。

## 実行時間

```
/kiwa-gap --metric duration --report {vitest json}
```

**絶対値は判定に使わない**。 同じ code で 6 倍振れる (11.5 / 29.9 / 30.6 / 69.9 秒、
計測時 load average 55.8)。 CPU 時間でも 1.39 倍動き、静的な呼出箇所数は cost と相関しない。

読むのは **順位と lever 別の偏り**。 順位は 4 run の相関 0.934 - 0.967 で安定する。

### 偏りを必ず見る

遅い順に並べるだけでは足りない。 実測で `tests/release-smoke` は 164.6 秒のうち
**131.1 秒 (80%) が `subprocess` lever** に集中していた。 並べただけでは「32 file 直す」 に
見えるが、偏りを見れば「子プロセス起動を 1 回に畳む」 の 1 手に絞れる。

### lever と直し方

| lever | 直し方 |
|---|---|
| `real-io` | container / anvil / browser を共有 fixture へ寄せる |
| `subprocess` | 1 回に畳むか module を in-process で import する |
| `compile` | 1 度だけ parse して結果を共有する |
| `wall-clock` | fake timer に置き換える |
| `filesystem` | 一時 dir を 1 つ共有して中身だけ差し替える |
| `inherent` | 出所が読み取れない。 実測して調べる (「直し方が無い」 ではない) |

### duration に達成条件は無い

`/kiwa-loop --metric duration` は **1 round だけ回して止まる**。 gap の先頭 1 件を直し、
何をどう変えたかを report に書いて終わる。 「速くなったか」 は測れないので判定しない。

前 round との差を「改善」「悪化」 と読まない。 負荷で動いた値を根拠に判断することになる。

## 完了条件に書く 1 行

各 SKILL.md はこう書く。

```
- カバレッジと実行時間は `references/coverage-contract.md` に従う (100% を目指し、
  届かない分は 4 分類の理由を report に記録済)
```

判定基準をこの 1 行の外に書き写さない。 書き写すと 1 箇所直した時に他が古いまま残る。
