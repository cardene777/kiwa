# lean

`@kiwa-lab/lean` は、アプリケーションの状態遷移表を Lean 4 の検証対象へ変換し、表そのものと実装の振る舞いを別々に確かめる TypeScript ライブラリです。認証のログイン状態、注文処理、ジョブの実行状態のように、「この状態でこの操作を受けたらどうなるか」を全組み合わせで決める必要がある場面に使います。

このライブラリが扱うのは状態機械です。状態とイベントを列挙し、各組み合わせを遷移先または拒否として記述します。生成された Lean ソースには全ての組み合わせが個別の分岐として現れ、catch-all 分岐は置かれません。行を落とせば Lean の網羅性検査が失敗するため、表の書き漏れを通常のユニットテストより早く見つけられます。

## このライブラリが確かめること

最初の層は仕様表です。既定では、表にない状態とイベントの組み合わせが一つでもあれば `generateLeanSpec` が生成を止めます。大半の組み合わせを拒否する設計なら `unspecified: 'invalid'` を明示して、未記入を拒否として扱えます。自己遷移は拒否ではありません。たとえば `active` で `refresh` を受けて `active` に留まることは受理された判断であり、到達不能な操作を拒否することとは区別されます。

`initial` を渡すと、全状態へ到達する短いイベント列を生成時に求めます。到達できない状態があれば、型だけに存在する状態として報告されます。`terminal` を渡すと、宣言した終端状態と実際に外へ出られない状態が一致するかを確かめます。イベントを受け付けるが外へ出られない sink 状態も区別して検出します。

次の層は Lean の実行です。`verifyLeanSpec` は生成したソースを一時領域で Lean に渡し、`ok` のときだけ検証できたと返します。`lean-not-installed`、`timed-out`、`output-too-large`、`skipped-by-env` はどれも合格ではありません。生成が成功したことと、Lean がソースを検査したことは別の事実です。

最後の層は実装です。`checkConformance` は状態とイベントの全セルについて observer を呼び、実装が遷移したか拒否したかを仕様表と比較します。仕様が正しくても実装が別の状態へ進めば差分として返るため、Lean の表だけを確認して実装テストを省略する用途には向きません。

## 使う判断

状態やイベントが増え、テストケースを手で列挙しているなら導入候補です。特に、拒否すべき操作が多い認証・権限・ライフサイクルの設計で効果が出ます。一方で、単純な入力変換や、状態を持たない関数に Lean を持ち込む必要はありません。このライブラリは状態機械の表を検査するもので、プロパティテスト、E2E テスト、実サービスの障害試験を置き換えるものではありません。

## 読み進める

[Quickstart](./quickstart) で小さな状態機械をテストとして保存し、生成と実装比較を実行します。[使い方](./how-to) では Lean の検証結果を CI で扱う方法と、差分の調査方法を説明します。[リファレンス](./reference) では入力形式と結果の全項目を確認できます。

Kaname で形式検証の対象を整理したい場合は [kaname](../kaname/) を参照してください。共有する仕様構造は [core](../core/) にあります。
