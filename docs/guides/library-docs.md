# ライブラリ文書を更新する

ライブラリの利用者向け本文は `docs/libraries` を正本として管理します。package の README と `packages/*/docs/README.md` は、npm と GitHub から同じ公開ページへ案内する入口です。

## 編集する場所

ライブラリごとに、カテゴリ配下の4ページを編集します。

- `index.md` は対象、採用判断、実行経路を説明します。
- `quickstart.md` は最小の成功ケースを実行可能なコードで示します。
- `how-to.md` は代表シナリオの分岐、失敗、終了処理を扱います。
- `reference.md` は公開 API、設定、制約を説明します。

package の README に本文を複製しません。短い install 例と公開文書へのリンクを保ちます。

## 文書種別の呼び方

日本語のサイトなので、画面に出る呼び方は日本語に統一します。
file 名と URL は英語のまま変えません。読者が見る言葉と、経路を指す識別子を分けます。

| file | URL | 画面に出る呼び方 |
|---|---|---|
| `index.md` | `/libraries/<分類>/<名前>/` | 概要 |
| `quickstart.md` | `/libraries/<分類>/<名前>/quickstart` | はじめる |
| `how-to.md` | `/libraries/<分類>/<名前>/how-to` | 使い方 |
| `reference.md` | `/libraries/<分類>/<名前>/reference` | リファレンス |

呼び方の正本は `docs/libraries.json` の `documentKinds` です。
これを変えるとライブラリの sidebar に反映されます。

反映されるのは sidebar だけです。
上の表と入口ページ (`docs/index.md`) の本文は markdown に直接書いてあるので、
呼び方を変えるときは 3 箇所をまとめて直します。
本文で文書種別に言及するときも、同じ言葉を使います。

分類・分類ごとの package 一覧・別枠で扱う文書も同じ file が正本です。
sidebar (`docs/.vitepress/config.mts`) と整合検査 (`scripts/check-docs-consistency.mjs`) の
両方がここを読むため、片方だけがずれることはありません。

正本をデータだけの JSON にしてあるのは、読む側が評価せずに済ませるためです。
検査 script は repo の内側にあることを確かめてから読み込みます。

## 本文の基準

公開ページは API 名の一覧や機能の箇条書きでは終えません。利用者が「自分のケースに使えるか」「最初に何を書けばよいか」「失敗したらどこを見ればよいか」を、ページを行き来せずに判断できることを基準にします。箇条書きは短い選択肢、前提、手順の確認だけに使います。本文の代わりに機能やリンクを並べず、各項目が利用者の入力、処理、結果、判断にどう結び付くかを文章で説明します。

概要は、対象にする処理を入力から結果までの文章で説明し、再現しない実サービスの振る舞いも明示します。用途の列挙は採用判断に必要な場合だけに留め、同じ内容を箇条書きで繰り返しません。はじめるは install、最小の実行例、期待する結果、テストを分離する理由を順に書きます。使い方は代表的な選択や失敗経路を取り上げ、どの入力で結果が変わるかと、実環境で検証すべき境界を説明します。リファレンスは public export の列挙だけでなく、既定値、戻り値、失敗条件、状態の寿命を説明します。

はじめるのコードは保存する file 名、実行する command、成功時に確認できる出力または assertion までを一続きで示します。利用者が補完できない前提や暗黙の setup を残しません。使い方のコードは、ページ内の import と cleanup を含む一つの保存可能な file として提示します。断片を積み上げて利用者に結合させません。使い方は代表 test または再現用 file の実行 command を添え、失敗した場合にどの条件を見直すかを説明します。外部 provider、browser、queue、database などを使う場合は、mock で確認できる範囲と実環境で確認する範囲を分けます。

専用 skill があるライブラリは、はじめるから [skills guide](/guides/skills) へ導き、起動 command、生成物を確認する手順、生成後に実行する test command を具体的に記載します。専用 skill がないライブラリに、存在しない自動化手順を作りません。

コード例は公開 entry point と代表 test で確認してから載せます。未実装の provider 挙動、推測した既定値、見た目だけのサンプルを書きません。API 宣言を同期する生成物は調査の入口であり、利用ガイドの代わりにはなりません。

見出しにはコロン、全角コロン、括弧を使いません。Mermaid は使わず、処理の分岐や依存関係を図で説明する必要があるときは静的 PNG を使います。番号は手順を表すときだけ使い、サイドバーや見出しには付けません。

## 更新手順

1. README、package metadata、公開 entry point、代表 test を確認します。
2. 対応する4ページを更新します。実装の変更で API、既定値、失敗条件、cleanup が変わる場合は必ず反映します。
3. 概要、はじめる、使い方、リファレンスがそれぞれ異なる問いに答えているかを読み返します。機能名の列挙だけになっている箇所は、利用者の入力、期待する結果、判断に必要な境界へ書き換えます。はじめるの command と期待結果、使い方の保存可能な file、失敗時の判断、実環境の境界も確認します。本文を削って箇条書きへ置き換えていないことも確認します。
4. 実行経路または依存関係が文章だけでは追いにくい場合は、`images/` に静的 PNG 図を追加します。図は `article-diagram-styles` と `imagegen` で生成し、装飾ではなく選択や分岐の判断に使います。
5. `pnpm docs:links:write` で package README と package-local docs の案内を同期します。
6. `pnpm docs:api-reference:write` で API リファレンスを再生成し、差分を確認して commit します。
7. `pnpm docs:build` を実行します。

`docs:links` と `docs:api-reference` は検査のみで、書き込みません。
名前に `:write` が付くものだけが file を更新します。
生成物を commit し忘れたまま build すると、`docs:build` は書き換えずに不一致を報告して止まります。

## 図を置く判断

概要では、入力から結果までの境界や依存関係を図にします。使い方では、正常系と失敗時の分岐、非同期処理、resource cleanup を図にします。単一の API 呼び出しや短い一覧は、コード例または表の方が読みやすいため図にしません。

## package の案内を確認する

同期スクリプトは、`docs/libraries` に4ページがある package を検出し、README と `docs/README.md` の `kiwa-docs` 範囲だけを更新します。公開 URL とリポジトリ内の編集元を両方記載するため、npm、GitHub、ローカル checkout のどこからでも正本へ到達できます。
