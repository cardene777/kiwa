## What's new (opt in)

### `@kiwa-lab/release-invariants` v0.1 — 3 invariant checkers + 1-shot aggregator

Install the package.

```bash
pnpm add -D @kiwa-lab/release-invariants@^0.1
```

Import the checkers.

```ts
import {
  buildReleaseInvariantsSummary,
  checkGateScriptPackageCoverage,
  checkProvenanceFlagAbsence,
  checkReleaseScriptFilter,
  type PublishablePackage,
  type ReleaseInvariantsSummary,
} from '@kiwa-lab/release-invariants';
```

Use them in your own release-smoke suite.

```ts
import { describe, expect, it } from 'vitest';
import { readFileSync } from 'node:fs';
import { resolve } from 'node:path';
import { buildReleaseInvariantsSummary } from '@kiwa-lab/release-invariants';

describe('release invariants', () => {
  it('all 3 invariants hold for the current root package.json', () => {
    const root = JSON.parse(readFileSync(resolve('package.json'), 'utf8'));
    const summary = buildReleaseInvariantsSummary({
      releaseScript: root.scripts?.release ?? '',
      mutationGateScript: root.scripts?.['test:mutation'] ?? '',
      publishable: [
        { name: '@kiwa-lab/core' },
        { name: '@kiwa-lab/realtime' },
        // ... every publishable package name here
      ],
    });
    expect(summary.ok).toBe(true);
  });
});
```

The 3 invariants are pure functions — no I/O, no side effects, no vitest dependency inside the package (vitest is only a devDep for the internal test suite). Downstream repos can call them from any test runner or a plain node script.

### Fail-fast release-smoke axis — `tests/release-smoke/tests/release-script-filter.test.ts`

Landed in v1.29-1 (PR #989). Dynamic package discovery walks `packages/*/package.json`, filters by `@kiwa-lab/*` scope + `private: false`, and runs 40 per-package assertions against the root `package.json` release script (build filter + publish filter halves).

The suite is opt-in via `pnpm --filter kiwa-release-smoke run test` — the existing 4 release-smoke tests (coverage-diff, coverage-gate, import-surface, v1-28-publish before this milestone; v1-29-publish after) keep passing without modification.

### PostToolUse hook + `/issue-plan` checklist

Landed in v1.29-2. When Write / Edit edits `packages/*/package.json`, the hook checks the root `package.json` release script for the package's filter presence and warns (does not hard-deny) if either half is missing. The `/issue-plan` skill body embeds a checklist for new package additions so the invariant is called out in the Issue body before implementation begins.

### Snippet validation — 7-milestone streak

`packages/release-invariants/tests/docs-tutorial-v1.29.test.ts` re-runs every code snippet from `docs/tutorials/55-release-script-filter-ssot.md` against the real `@kiwa-lab/release-invariants` v0.1 API. This continues the 6-milestone streak (v1.23 payment / v1.24 edge / v1.25 perf-harness / v1.26 orm / v1.27 quality-metrics / v1.28 realtime) with `docs-tutorial-v1.29.test.ts` making it a 7-milestone streak — any snippet drift is structurally blocked.

## Publishing your own release-invariant checks

The 3 invariants are the SSOT for kiwa, but the pattern generalises. A downstream monorepo can wrap the checkers with its own `PublishablePackage` source (e.g. Turborepo, Nx, Lerna) and get the same fail-fast semantics.

- **Source the publishable list** — walk `packages/*/package.json` (or the monorepo tool's package graph), filter by scope prefix + `private: false`.
- **Source the release script** — read `scripts.release` from the root `package.json`.
- **Source the mutation gate script** — read `scripts.test:mutation` (or whichever gate script your mutation runner uses).
- **Assert** — pass all three to `buildReleaseInvariantsSummary` and expect `summary.ok === true`.

## FAQ

- **Do I need to migrate existing test suites?** No. v1.29 is opt-in. Existing suites keep working with zero changes.
- **What about `@kiwa-lab/quality-metrics`?** Unchanged. v1.29 does not extend the 11-axis release gate. Release-invariants are a separate SSOT because they check the release script itself, not the release quality signal.
- **Can I use the invariants outside kiwa?** Yes. The 3 checkers are pure functions with no kiwa-specific dependencies. Any pnpm monorepo can call them.
- **What if I want to add a 4th invariant?** Open an Issue with the specific failure mode and a proposed check signature. v1.29 pins the 3 that recurred 4 times each in the v1.11 - v1.28 window — future additions need matching evidence.
