# Migration guide — v1.31 → v1.32

v1.32 is **additive** — every `@kiwa/*` package public API that existed in v1.31 keeps its surface. Existing tests keep passing without touching a single line. The v1.32 changes are pure additions on the database 深化 II axis (Postgres logical replication advanced + MySQL cluster group replication + SQLite WAL + FTS5 + txn isolation + advanced pool + real driver env-gate).

The 5 things v1.32 adds are.

- `@kiwa/orm` v0.10 — 8 advanced-semantics axes on top of the v0.9 8-semantics base (`createLogicalReplicationAdvancedSession` + `createMvccAdvancedSession` + `createMysqlClusterSession` + `createBinlogSession` + `createSqliteWalSession` + `createFts5Session` + `createTxnIsolationSession` + `createPoolAdvancedSession`) + a `collectFidelityCoverage()` describing the 3 provider × 3 backend × 16 axis grid (144 cells) + a `KIWA_MODE=real` env-gate that lets the same assertions run against real Postgres 16 / MySQL 8 / SQLite testcontainers when the corresponding `POSTGRES_KEY` / `MYSQL_KEY` / `SQLITE_KEY` env is present.
- 3 dogfood app v2 upgrades (`examples/dogfood-postgres-cdc-outbox-app` v2 + `examples/dogfood-mysql-rls-tenant-app` v2 + `examples/dogfood-sqlite-wal-fts-app` new) — each pins to real Postgres 16 / MySQL 8 / SQLite (libsql) under testcontainers, routes the fidelity-harness assertions through Playwright e2e, and keeps the mock-only path green for the fast inner loop. The v1.29 3-layer defensive structure (release-invariants + docs-e2e + release-smoke) auto-fires on merge.
- 3 new tutorials (61 Postgres logical replication advanced + 62 MySQL group replication + 63 SQLite WAL + FTS5) + 1 concept doc SSOT (`database-real-driver-testing.md` — 16 axis SSOT + 144 cell grid + testcontainers pattern + real driver env-gate + backend-specific `_KEY` envs) + 1 migration guide (this file) + 1 snippet validation test (`packages/orm/tests/docs-tutorial-v1.32.test.ts`) — **10-milestone snippet validation streak** (v1.23 → v1.32). All wired through the sidebar (`docs/.vitepress/config.mts`).
- 3 `examples/dogfood-*` v2 / new real-driver integrations (Postgres + MySQL + SQLite) — each dogfood app ships a `docker-compose.yml` for `KIWA_MODE=real` runs + a Playwright e2e that walks the 8-axis surface + a fidelity harness assertion that the mock-vs-real cells match. Existing dogfood v1 flows keep working; v2 layers a real-driver row on top; the SQLite WAL+FTS app is new so v1 mock coverage is baseline.
- No new release-gate axis — v1.32 stays at the v1.30 13-axis lineup (`a11y.tier` was the 13th). The 8 database axes are surface-level (they gate the orm package's own tests) but do not surface as a per-package release-gate axis, because the fidelity harness lives inside `@kiwa/orm` rather than at `@kiwa/quality-metrics`.

## What's new (opt in)

### `@kiwa/orm` v0.10 — 8 advanced-semantics axes

Install (or bump) the package.

```bash
pnpm add -D @kiwa/orm@^0.10
```

Import the axis you need.

```ts
import {
  createLogicalReplicationAdvancedSession,
  createMvccAdvancedSession,
  createMysqlClusterSession,
  createBinlogSession,
  createSqliteWalSession,
  createFts5Session,
  createTxnIsolationSession,
  createPoolAdvancedSession,
  collectFidelityCoverage,
} from '@kiwa/orm';
```

Use it in your own test.

```ts
import { describe, expect, it } from 'vitest';
import {
  createLogicalReplicationAdvancedSession,
  startLogicalStreaming,
  trackReplicationOrigin,
  confirmTwoSafeCommit,
} from '@kiwa/orm';

describe('my subscriber — two-safe commit', () => {
  it('advances confirmedLsn when >= 1 synchronous standby applies', () => {
    const session = createLogicalReplicationAdvancedSession({
      streamId: 'orders-outbox',
      provider: 'drizzle',
      backend: 'postgres',
    });
    startLogicalStreaming(session, { startLsn: 42_000_000, protocolVersion: 2 });
    trackReplicationOrigin(session, { originId: 'sub_orders', remoteLsn: 42_010_000 });

    const step = confirmTwoSafeCommit(session, {
      confirmedFlushLsn: 42_020_000,
      synchronousStandbys: 2,
    });

    expect(step.state).toBe('two-safe-confirmed');
    expect(step.backendEvent).toBe('synchronous_commit.remote_apply');
  });
});
```

The full API surface — 4 functions per axis × 8 axes = 32 new state-machine transitions — is spelled out in tutorials 61 (logical-replication-advanced), 62 (mysql-cluster), 63 (sqlite-wal + fts5). The 4 other axes (`mvcc-advanced` / `binlog` / `txn-isolation` / `pool-advanced`) follow the same "explicit state, explicit metadata, backend dialect resolver" pattern.

### `collectFidelityCoverage()` — 3 provider × 3 backend × 16 axis = 144 cell grid

The fidelity harness describes which provider × backend pair covers which axis and what neutral event + backend dialect each axis emits.

```ts
import { collectFidelityCoverage } from '@kiwa/orm';

const coverage = collectFidelityCoverage({
  providers: ['drizzle', 'prisma', 'kysely'],
  backends: ['postgres', 'mysql', 'sqlite'],
});

console.log(coverage.rows.length); // 144
console.log(coverage.axes.length); // 16

const postgresLogicalAdv = coverage.rows.find(
  (r) => r.provider === 'drizzle' && r.backend === 'postgres' && r.axis === 'logical-replication-advanced',
);
console.log(postgresLogicalAdv?.backendEvents);
// [ 'pgoutput.start_replication', 'pg_replication_origin.progress',
//   'synchronous_commit.remote_apply', 'pg_subscription.cascade_synced' ]
```

Every one of the 144 rows has a `neutralEvent` list (portable) and a `backendEvent` list (backend-specific dialect). Tests iterating the grid assert on the neutral name for portability; tests wired to real backend telemetry can assert on the backend-specific dialect. This is the data structure the release-gate report reads to render "the fidelity matrix" in the CI summary.

### `KIWA_MODE=real` — env-gated real driver run

The mock path stays the default. When `KIWA_MODE=real` is set, the harness assertions also try to run against the real driver, gated by the required env for that backend.

- **Postgres** axes → `POSTGRES_KEY`
- **MySQL** axes → `MYSQL_KEY`
- **SQLite** axes → `SQLITE_KEY`

Absent env means skip the real-driver assertion (mock path stays green). This is the same env-gate contract the v1.22 real-driver testing tutorial (auth adapters + Keycloak) and the v1.31 streaming real-driver concept doc use. Backend-neutral axes (`txn-isolation` / `pool-advanced`) run against whichever backend the test's `provider` + `backend` fields point at.

## Snippet validation — 10 milestone streak

`packages/orm/tests/docs-tutorial-v1.32.test.ts` — every code snippet in tutorials 61-63 is behavior-tested. If the orm API surface drifts, the snippet test fails before the tutorial hits a reader.

The streak is now 10 milestones (v1.23 → v1.32) — each milestone lands a `docs-tutorial-v{version}.test.ts` in its package of record with `describe('tutorial N — {topic}')` blocks that mirror the tutorial code. This is the pattern kiwa uses to keep the docs from drifting silently; 10 consecutive milestones with the pattern makes it the default rather than the exception.

Read this once when you first onboard the orm advanced-semantics package; the tutorials build on top of it.

## No release-gate axis change

v1.32 does not add a 14th release-gate axis. The 8 database axes gate the orm package's own tests (via `pnpm --filter @kiwa/orm test`) but do not surface as a per-package `quality-metrics` axis. The reason is that the fidelity harness is backend-shape-specific — a package that does not use Postgres / MySQL / SQLite has nothing to assert on. When a future milestone adds a `backend.fidelity` axis that describes "which backends this package's tests hit," it will slot into the 13-axis release gate as the 14th; v1.32 keeps things simple.
