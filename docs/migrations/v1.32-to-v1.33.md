# Migration guide — v1.32 → v1.33

v1.33 is **additive** — every `@kiwa-test/*` package public API that existed in v1.32 keeps its surface. Existing tests keep passing without touching a single line. The v1.33 changes are pure additions on the payment 深化 II axis (orchestration + revenue recovery + refund advanced + dispute lifecycle + webhook idempotency advanced + tax localization + subscription state machine + payment method vault + real driver env-gate).

The 5 things v1.33 adds are.

- `@kiwa-test/payment` v0.4 — 8 advanced-semantics axes on top of the v0.3 9-semantics base (`startOrchestration` + `routeCharge` + `probeCircuit` + `startRecovery` + `scheduleSmartRetry` + `advanceCascade` + `applyCardUpdate` + `applyNetworkToken` + `finalizeRecovery` + `startRefund` + `partialRefund` + `fullRefund` + `denyByPolicy` + `markWindowExpired` + `preventChargeback` + `openDispute` + `submitDisputeEvidence` + `representDispute` + `escalateArbitration` + `shiftLiability` + `finalizeDispute` + `startIdempotency` + `deliver` + `reportFailure` + `rotateSignature` + `calculateLocalizedTax` + `reportDac7` + `startSubscriptionMachine` + `enterGracePeriod` + `exitGracePeriod` + `applyProration` + `stackCoupon` + `startVault` + `tokenizeCard` + `revokeToken` + `migrateToken` + `verifyPciScope`) + a `collectFidelityCoverage()` describing the 3 provider × 17 axis (v0.3 9 + v0.4 8) grid (51 rows, of which 24 belong to the v0.4 slice) + a `KIWA_MODE=real` env-gate (`resolveMode` / `resolveAllModes` / `assertMode`) that lets the same assertions run against real Stripe test mode + Paddle sandbox + Lemon Squeezy sandbox when the corresponding `STRIPE_KEY` / `PADDLE_KEY` / `LEMONSQUEEZY_KEY` env is present.
- 3 dogfood app v2 / new upgrades (`examples/dogfood-stripe-marketplace-app` v2 + `examples/dogfood-paddle-subscription-app` v2 + `examples/dogfood-lemonsqueezy-license-app` new) — each pins to real Stripe test mode / Paddle sandbox / Lemon Squeezy sandbox under `KIWA_MODE=real`, routes the fidelity-harness assertions through Playwright e2e, and keeps the mock-only path green for the fast inner loop. The v1.29 3-layer defensive structure (release-invariants + docs-e2e + release-smoke) auto-fires on merge.
- 3 new tutorials (64 Payment orchestration + 65 Stripe Connect marketplace + 66 Paddle Billing v2) + 1 concept doc SSOT (`payment-real-driver-testing.md` — 8 axis SSOT + 24 cell grid + testcontainers-shaped env-gate pattern + real driver env-gate + provider-specific `_KEY` envs) + 1 migration guide (this file) + 1 snippet validation test (`packages/payment/tests/docs-tutorial-v1.33.test.ts`) — **11-milestone snippet validation streak** (v1.23 → v1.33). The 8 payment axes are surface-level (they gate the payment package's own tests) but do not surface as a per-package release-gate axis, because the fidelity harness lives inside `@kiwa-test/payment` rather than at `@kiwa-test/quality-metrics`.

### `collectFidelityCoverage()` — 3 provider × 17 axis grid (24 cells for the v0.4 slice)

The fidelity harness describes which provider covers which axis and what neutral event + provider dialect each axis emits.

```ts
import {
  collectFidelityCoverage,
  createStripeMock,
  createPaddleMock,
  createLemonSqueezyMock,
} from '@kiwa-test/payment';

const coverage = collectFidelityCoverage([
  createStripeMock({ secret: 'whsec_stripe' }),
  createPaddleMock({ secret: 'whsec_paddle' }),
  createLemonSqueezyMock({ secret: 'whsec_lemonsqueezy' }),
]);

console.log(coverage.rows.length); // 51 (3 provider × 17 axis)
console.log(coverage.axes.length); // 17 (9 v0.3 + 8 v0.4)

const stripeOrch = coverage.rows.find((r) => r.provider === 'stripe' && r.axis === 'orchestration');
console.log(stripeOrch?.neutralEvents);
// [ 'orchestration.routed', 'orchestration.failed_over',
//   'orchestration.circuit_opened', 'orchestration.circuit_closed' ]
```

Every one of the 51 rows has a `neutralEvents` list (portable) and a `providerEvents` list (provider-specific dialect). Tests iterating the grid assert on the neutral name for portability; tests wired to real provider webhooks can assert on the provider-specific dialect. This is the data structure the release-gate report reads to render "the fidelity matrix" in the CI summary.

### `KIWA_MODE=real` — env-gated real driver run

The mock path stays the default. When `KIWA_MODE=real` is set, the harness assertions also try to run against the real driver, gated by the required env for that provider.

- **Stripe** axes → `STRIPE_KEY` (Stripe test-mode `sk_test_*`)
- **Paddle** axes → `PADDLE_KEY` (Paddle sandbox API key)
- **Lemon Squeezy** axes → `LEMONSQUEEZY_KEY` (Lemon Squeezy sandbox API key)

Absent env means skip the real-driver assertion (mock path stays green). This is the same env-gate contract the v1.22 real-driver testing tutorial (auth adapters + Keycloak), the v1.31 streaming real-driver concept doc, and the v1.32 database real-driver concept doc all use. The `resolveMode(provider, env)` helper reports one of 4 reasons — `default-mock` / `kiwa-mode-real` / `missing-key` / `invalid-mode` — so callers can distinguish "opted out" from "misconfigured."

## Snippet validation — 11 milestone streak

`packages/payment/tests/docs-tutorial-v1.33.test.ts` — every code snippet in tutorials 64-66 is behavior-tested. If the payment API surface drifts, the snippet test fails before the tutorial hits a reader.

The streak is now 11 milestones (v1.23 → v1.33) — each milestone lands a `docs-tutorial-v{version}.test.ts` in its package of record with `describe('tutorial N — {topic}')` blocks that mirror the tutorial code. This is the pattern kiwa uses to keep the docs from drifting silently; 11 consecutive milestones with the pattern makes it the default rather than the exception.

## No release-gate axis change

v1.33 does not add a 14th release-gate axis. The 8 payment axes gate the payment package's own tests (via `pnpm --filter @kiwa-test/payment test`) but do not surface as a per-package `quality-metrics` axis. The reason is that the fidelity harness is provider-shape-specific — a package that does not use Stripe / Paddle / Lemon Squeezy has nothing to assert on. When a future milestone adds a `provider.fidelity` axis that describes "which payment providers this package's tests hit," it will slot into the 13-axis release gate as the 14th; v1.33 keeps things simple.
