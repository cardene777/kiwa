## Fidelity summary (mock vs real, 4 ceremony patterns)

Cross-report roll-up. Each detail report keeps its own axis table; this one
just names which patterns are green.

| pattern | mock rows | real rows | detail report |
|---|---|---|---|
| register-attestation (#856) | 4 axes green (`attestationObject` shape / `clientDataJSON` shape / signature format / `signCount=0`) | env-gated (spec-based assertion — `KIWA_WEBAUTHN_REAL_READY=1` opts in) | `webauthn-passkey-app-register.md` |
| signin-assertion (#857) | 3 axes green (base64url signature / monotonic `signCount` / credentialId round-trip) | Chrome Virtual Authenticator exercises the browser side via Playwright; RP mock is the verifier | (folded here) |
| userVerification (#858) | 6 axes green (`required`+UV / `required`+noUV / `preferred`+UV / `preferred`+noUV / `discouraged` / `impossible`) | spec-based assertion for `real` — same schema-layer rejection semantics as SimpleWebAuthn | `webauthn-passkey-app-user-verification.md` |
| residentKey + `/manage` (#859) | 6 axes green (creation × 4 residentKey values / discovery / delete) | spec-based assertion for `real` — same `residentKey requirement not satisfied` semantics | `webauthn-passkey-app-resident-key.md` |

All four patterns keep the same fidelity contract shape: mock rows are
executed by vitest; real rows are executed by Playwright + Chrome Virtual
Authenticator inside a browser context, and the RP mock (which is the
verifier) receives the browser-generated bytes. A future PR wires
`makeRealAdapter` (`src/adapters/real.ts`) through the same Playwright harness
so the real-adapter code path is exercised in addition to the browser side.

## Known follow-ups (out of scope for #843)

- Real adapter — `KIWA_WEBAUTHN_REAL_READY=1` still gates `makeRealAdapter`
  behind `KIWA_WEBAUTHN_ENV_MISSING`. Wiring the real adapter through the
  Playwright harness (so both browser-side + RP-side are exercised) is a
  follow-up PR once the SimpleWebAuthn-shaped RP server lands upstream in
  `@kiwa/auth`.
- Cross-user credential scoping — the RP store keys by `credentialId` only.
  A production Passkey RP scopes by `userHandle` + filters `/manage` list to
  the signed-in user. Sub-Issue #859's detail report notes this SCOPE
  BOUNDARY.
- Step-up on `/manage` — the dogfood surface is intentionally open because
  the app is single-user. Adding session-cookie gating + a fresh
  `webauthn.get` assertion before mutating the store is a real-app follow-up.
